# Chalezinho Ville — homologação ponta a ponta em DEV

Esta rodada verifica a versão que o hóspede e a equipe realmente usam: tela → API → banco → PagBank sandbox, quando aplicável. Entrega: evidências, matriz preenchida e fila de correções. A rodada de auditoria não altera o produto; a etapa seguinte implementa e retesta os achados em DEV.

## Ambiente e limites

1. Base do produto: commit `3dc9e9c66af1dcde98cf9fa492081828c04399d0` da branch `fix/cancellation-policy-integrity-20261105`. A branch deste roteiro acrescenta somente documentos. Use a prévia DEV indicada no pedido, confira o commit que ela serve e registre o SHA e a versão das funções realmente chamadas. Se a prévia mudar, informe a diferença antes de comparar os resultados.
2. Confirme o perfil `checkout-development`, a URL e o projeto Supabase DEV definidos em `app-config.js` e `supabase/functions/_shared/release-policy.ts`, e o PagBank sandbox conforme `docs/finance/`. Valide ambiente e gateway antes da primeira escrita e a cada troca de URL. Se não for possível confirmar o destino, interrompa as escritas e siga com testes locais. Nunca use PROD, domínio público de produção, cobranças reais ou credenciais de produção.
3. Use duas contas de hóspede A/B e, quando necessário, papéis DEV de administrador/anfitrião/equipe. Use contas e registros sintéticos exclusivos da rodada. Utilize apenas cartões e dados fictícios oficialmente suportados pelo sandbox. Não use nem consulte registros de hóspedes reais para reproduzir falhas. Teste confirmação/reset/recibos apenas em caixa de teste autorizada, sem disparos a terceiros.
4. Use inventário de teste isolado, sem sincronização de calendários ou preços com Airbnb, Booking, PriceLabs ou outros canais reais. Se não houver imóvel sintético compatível, não reserve datas reais: marque o teste bloqueado e identifique o recurso que falta. Não altere permissões permanentes, configuração global compartilhada ou proteção da prévia para facilitar a rodada. Para troca de política, use uma instância isolada que reproduza o DEV ou uma janela com autorização específica; não mude a política vigente do DEV compartilhado só para testar.
5. Teste vulnerabilidades somente nos alvos DEV indicados e com contas próprias de teste, volume baixo, entradas inofensivas e escopo mínimo. Não faça força bruta, carga, extração em massa, persistência, envio de dados a sites externos nem varredura de serviços de terceiros. Se houver exposição, pare o cenário na primeira prova segura e registre apenas o mínimo necessário.
6. O repositório é público. Publique no Git apenas conclusões sanitizadas. Nunca suba tokens, cookies, chaves, credenciais, e-mails, CPF, dados de cartão, nomes reais, identificadores de transação que permitam consulta, HAR/traces brutos, capturas sem revisão ou detalhes que permitam explorar uma falha ainda aberta. Evidência restrita, quando necessária, fica em local privado autorizado, com referência neutra no relatório público; se não houver destino seguro, registre a limitação sem anexar a evidência.
7. Se faltarem acessos, registre a barreira com página/etapa e continue os demais casos. Não desative SSO, não procure segredos no histórico e não compartilhe links de bypass. No fim, retire ou revogue apenas contas, permissões, dados e artefatos criados pela própria rodada. Confirme que não restaram bloqueios ou notificações de teste. Preserve o histórico necessário à auditoria do sandbox; não faça estornos adicionais só para “limpar”.

## Ordem de execução

1. Registre um ID de rodada `AAAA-MM-DD-HHMM-UTC`, a prévia, os SHAs, a data, os navegadores e o tamanho da tela. Leia também [a matriz histórica](../../homologation-current-matrix.md) e [a documentação financeira](../../finance/homologation.md). Use-as como contexto; resultados antigos não substituem evidências desta rodada.
2. Rode `npm run check`, `npm run typecheck`, `npm test` e `npm run test:browser` se houver navegador disponível. Veja `playwright.config.mjs`: a suíte padrão usa servidor local e pode simular respostas. Identifique teste local/simulado, API DEV, UI DEV e confirmação sandbox separadamente.
3. Execute P0 primeiro: login de hóspede A/B e administração, isolamento entre contas, checkout Pix/cartão, estados e duplicidade, cancelamento e estorno, política por reserva e caução. Use navegador no fluxo principal, APIs para validar o resultado e logs/banco DEV para confirmação. Em seguida cubra UX, operação e regressões.
4. Use celular e desktop no fluxo principal. Registre navegador, viewport e entrada por toque/teclado real ou emulada. Nos passos dependentes de tempo, use casos e relógios controlados em ambiente isolado ou aguarde a resposta real do sandbox. Não avance relógios nem regrave reservas do DEV compartilhado.
5. Acompanhe o percurso inteiro de cada caso, distinguindo “pedido registrado”, “operação enviada” e “confirmado pelo provedor”. Compare valores em centavos na interface, na API, no histórico e no gateway. Não repita ações financeiras incertas com uma nova chave: consulte e concilie primeiro.
6. Preencha uma linha por caso. Marque `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN` ou `N/A` com justificativa. Se um caso P0 depender de um componente inacessível, não marque a jornada como aprovada. Uma inspeção, um mock, ou HTTP 200 isolado não provam ponta a ponta.

## Handoff e correção

- **Codex Nuvem (QA):** crie uma branch `qa/dev-e2e-report-<rodada>` a partir desta branch de roteiro. Faça commit só dos relatórios sanitizados em `docs/qa/dev-e2e/relatorios/<rodada>/`. Informe a branch, o SHA do relatório, os caminhos e o estado de cada P0. Não mescle, não implante e não implemente correções nesta rodada.
- **Work (correções):** ao receber a branch, valide ambiente, SHA e evidência; reproduza cada falha confirmada. Corrija primeiro autorização, dinheiro, estoque e perda de dados, depois UX. Trabalhe em branch `fix/dev-e2e-<rodada>` a partir da base DEV confirmada, não de produção. Relacione cada correção ao ID do achado, adicione regressões, publique somente em prévia/DEV e registre a nova versão. Não publique em PROD.
- **Reteste:** repita os passos do achado na nova prévia, com dados novos. Feche apenas o que passou com evidência no mesmo nível em que falhou. Mantenha pendências externas separadas e aponte quem pode resolvê-las. A decisão desta rodada é sobre prontidão do DEV; homologação do provedor e liberação de produção são etapas distintas.
